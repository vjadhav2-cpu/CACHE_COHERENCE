# DMA/L2 Coherency Implementation Plan

## Date

July 30, 2026

## Purpose

Document how to close the coherency gap between:

- `cache_system/rv64g_l2_cache.v` / `rv64g_l2_fsm.v`
- DMA traffic entering the TLC fabric
- shared memory behind `tlc/tlc_slave_mem_manager.v`

This note is meant to be the future reference for the implementation, not
just a record of the problem.

## Problem Statement

Today L2 and DMA both reach the same memory through the TLC fabric, but
they do not participate in one shared coherence scheme.

- L2 tracks its own L1 sharers/owners in `rv64g_l2_directory.v`.
- The TLC side tracks master ownership in `tlc_slave_mem_manager.v`.
- `tlc/l2_tlc_bridge.v` currently sends L2 memory-side traffic as plain
  `Get` / `PutFullData`, using the uncached path through
  `l1_tilelink_adapter.v`.

Because of that, the TLC directory never records that L2 holds a line.
So when DMA writes to a cache line that L2 already has cached, memory is
updated but L2 is not probed, invalidated, or downgraded. L2 can
therefore keep serving stale data.

This hazard is already characterized in
`tlc/tb_dma_l2_coherency_gap.v`.

## Desired End State

The target behavior is:

1. L2 fetches and holds a cache line.
2. DMA tries to write the same line.
3. The TLC-side directory sees that L2 is a holder/owner of that line.
4. The TLC-side coherence engine sends a probe to L2.
5. L2 invalidates or downgrades the line, and returns dirty data if
   required.
6. DMA write completes only after the probe flow is complete.
7. A later L2/core read sees fresh data, not stale data.

In short: DMA and L2 must become coherent through the existing TLC
directory/probe machinery.

## Chosen Architecture

Use the existing coherence engine in `tlc/tlc_slave_mem_manager.v` as the
single point of arbitration between DMA and L2 at the shared-memory
boundary.

That means:

- L2 must stop appearing as an uncached client on the TLC side.
- `l2_tlc_bridge.v` must issue coherent transactions so the TLC directory
  records L2 in `dir_pres`.
- probes generated by the TLC manager must be delivered into L2 and
  answered correctly.

This is the preferred implementation because it reuses working,
already-integrated probe and directory logic instead of building a second
cross-domain coherence protocol.

## Why Not Make DMA Coherent Through L2 Instead

An alternate approach is to move DMA above L2 and make DMA look like
another coherent core client on L2's upstream TileLink port.

We are not choosing that path because it requires:

- rewriting the DMA-side bridge/client model
- changing L2 directory ownership accounting to include DMA
- retiring or bypassing the existing TLC-side directory for DMA/L2
  conflicts
- reworking the current system topology and testbenches

That is a much bigger architecture change than needed for this repo's
current structure.

## High-Level Implementation Strategy

### Phase 1: Make L2 visible to the TLC directory

Change `tlc/l2_tlc_bridge.v` so L2 memory-side transactions use coherent
request types rather than the uncached path.

Expected effect:

- TLC-side `dir_pres` starts tracking L2 (`m0`) as a line holder.
- DMA conflicts against the same line naturally trigger the existing
  probe FSM in `tlc_slave_mem_manager.v`.

### Phase 2: Make L2 respond to TLC probes

Add a new snoop/probe entry point into L2 so an external request from the
bridge can say:

"For address X, if you have this line, downgrade or invalidate it; if it
is dirty, provide the dirty data."

This is the new work that does not already exist in the current L2 flow.

### Phase 3: Verify end-to-end coherency

Update the coherency-gap test so it flips from:

- "stale data is expected and proves the hazard exists"

to:

- "fresh data is expected and proves the fix works"

## File-By-File Change Plan

### 1. `tlc/l2_tlc_bridge.v`

This file is the main bridge between L2's memory-side port and the TLC
master-slot interface.

#### Current behavior

- Decomposes each 64-byte L2 line access into 8 single-beat TLC-side
  transactions.
- Uses `L1_REQ_UNCACHED_READ` / `L1_REQ_UNCACHED_WRITE`.
- Ties off `probe_ack_from_l1_*` and ignores `probe_req_to_l1_*`.

#### Required changes

- Replace uncached request types with coherent request types:
  - line refill path: coherent read-miss / `AcquireBlock`
  - exclusive/modify path if needed: coherent write-miss /
    `AcquirePerm` or whichever adapter request type maps correctly
  - writeback/eviction path: `Release` / `ReleaseData`
- Keep the existing 8-beat decomposition model for now.
  This plan does not require a burst-capable adapter.
- Add E-channel completion handling when the coherent path returns
  `Grant` / `GrantData` that requires `GrantAck`.
- Stop hardwiring probe ack outputs to zero.
- Consume `probe_req_to_l1_valid`, `probe_req_to_l1_addr`,
  `probe_req_to_l1_permissions`.
- Add a bridge-side state machine for probe handling:
  - accept probe from TLC side
  - issue a snoop request into L2
  - wait for snoop response
  - translate the result into `ProbeAck` or `ProbeAckData`
- Track enough state to know whether the probe response should include
  data and what permissions transition was applied.

#### Important note

This bridge currently thinks only in terms of the mem-side burst flow.
After this change, it becomes both:

- a requester toward the TLC fabric
- a probe responder on behalf of L2

That dual role should be reflected explicitly in the bridge FSM
structure.

### 2. `cache_system/rv64g_l2_cache.v`

This module will likely need a new interface between the bridge and the
L2 internals.

#### Required changes

- Add a snoop/probe request input path from `l2_tlc_bridge.v`
- Add a snoop/probe response output path back to the bridge
- Plumb the new signals into `rv64g_l2_fsm.v`

Suggested signal family:

- `snoop_req_valid`
- `snoop_req_addr`
- `snoop_req_param`
- `snoop_req_ready`
- `snoop_rsp_valid`
- `snoop_rsp_has_data`
- `snoop_rsp_data`
- `snoop_rsp_param`

Exact names can change, but this separation should stay clear:

- request from bridge into L2
- completion from L2 back to bridge

### 3. `cache_system/rv64g_l2_fsm.v`

This is where the real L2-side coherence work must happen.

#### What already exists

The FSM already knows how to:

- look up tags and directory state
- probe L1s above L2
- wait for `ProbeAck` / `ProbeAckData`
- collect dirty data through its existing eviction machinery

In particular, the eviction path around `ST_EVICT_WAIT`,
`ST_MEM_WRITE`, and the directory update flow already performs most of
the operations needed for "force this line out of L2 and tell me whether
dirty data exists".

#### Missing capability

There is no external entry point today for a request coming from below
L2. Nothing can currently ask L2 to snoop a specific address and perform
an invalidate/downgrade sequence on demand.

#### Required changes

- Add a new externally-triggered snoop flow.
- Do an address-based lookup for the probed line.
- If the line is not present in L2:
  - return a clean "no copy" style response quickly.
- If the line is present:
  - determine whether the line is shared, owned, dirty, etc.
  - trigger the existing invalidate/writeback machinery
  - wait for any required internal L1 probe acknowledgements
  - return whether data had to be supplied
- Reuse as much of the existing eviction/probe machinery as possible.
  Do not create a fully separate invalidation engine if the current
  states can be parameterized.

#### Best implementation pattern

Introduce a small "request origin" or "operation mode" distinction:

- normal miss/evict flow
- externally-requested snoop flow

That lets the FSM reuse the same internal probe/wait/data-collection
states while changing only:

- the trigger
- the completion condition
- whether the next step is refill/writeback vs "report to bridge and end"

### 4. `cache_system/rv64g_l2_directory.v`

This file is not expected to need architectural changes if the current
read/write interfaces already expose:

- valid
- sharers
- owner-valid
- owner-id
- dirty

The implementation work should primarily be in the FSM's use of the
directory, not the directory RAM structure itself.

Still, verify the existing ports are sufficient for:

- lookup by external snoop address
- invalidate/update after a successful snoop operation

### 5. `tlc/l1_tilelink_adapter.v`

No major architecture rework is planned here, but it must be confirmed
that the coherent path used by `l2_tlc_bridge.v` is correct for:

- `AcquireBlock` / `AcquirePerm`
- `Grant` / `GrantData`
- `Release` / `ReleaseData`
- probe delivery on B
- probe acknowledgment return on C
- `GrantAck` on E

This adapter already contains the general probe and coherent message
structure, but some paths may have been lightly exercised in past tests.
Treat this as "verify carefully", not "assume correct".

### 6. `tlc/tlc_xbar_fabric_top.v`

This file is expected to stay structurally the same, but the master-0
probe path must be validated end-to-end.

Checklist:

- `m0_probe_req_*` from TLC fabric reaches `l2_tlc_bridge.v`
- `m0_probe_ack_*` from bridge returns into the adapter/fabric path
- B-channel source routing and C-channel response routing are both
  correct for slot `m0`

This path has been wired generically, but that is not the same thing as
having been truly exercised.

### 7. `tlc/tlc_slave_mem_manager.v`

This file is expected to stay functionally unchanged.

That is one of the main reasons this architecture is attractive.
Once L2 becomes visible in `dir_pres`, the existing flow should already
do the right thing:

- detect overlap between DMA request and L2 presence
- send probes
- wait for `ProbeAck` / `ProbeAckData`
- continue the DMA transaction only after coherence is resolved

The key objective is to make the existing manager aware of L2, not to
teach it a new algorithm.

## Expected Coherence Flow After The Fix

Example: DMA writes to a line currently cached in L2.

1. A core read causes L2 to fetch and hold line A.
2. `l2_tlc_bridge.v` obtained that line coherently, so the TLC manager
   recorded `m0` in its directory.
3. DMA issues a write touching line A.
4. `tlc_slave_mem_manager.v` looks up the line and sees `m0` present.
5. It sends a probe to master slot `m0`.
6. The probe reaches `l2_tlc_bridge.v`.
7. The bridge converts that probe into an L2 snoop request.
8. L2 checks whether it has the line.
9. If present, L2 invalidates or downgrades it.
10. If dirty, L2 returns data for `ProbeAckData`; otherwise it returns a
    clean `ProbeAck`.
11. The bridge forwards that response through the TLC path.
12. The TLC manager completes its probe wait state.
13. DMA write proceeds to memory.
14. A later L2 access must miss or re-fetch and observe fresh data.

## Verification Plan

### Primary regression

Use `tlc/tb_dma_l2_coherency_gap.v` as the main proof point.

Current expectation:

- stale data after DMA write
- no extra memory read on L2 re-access

Post-fix expectation:

- L2 must not return stale data
- L2 re-access must either:
  - observe fresh data after a refill, or
  - observe fresh data after a legal downgrade/update path

### Additional checks

- Add waveform-visible assertions or `$display` markers for:
  - probe issued to `m0`
  - snoop request launched into L2
  - snoop response returned
  - `ProbeAck` vs `ProbeAckData`
- Confirm DMA transaction does not retire before the L2 probe completes.
- Confirm memory contents still match the DMA-written pattern.
- Confirm unrelated DMA-only and L2-only regressions still pass.

### Regression list

- `tlc/tb_l2_tlc_bridge_standalone.v`
- `tlc/tb_tlc_l2_dma_shared_mem.v`
- `tlc/tb_dma_l2_coherency_gap.v`

If practical, also rerun:

- `tlc/tb_tlc_dma_system_basic_v3.v`

with the known caveat that its pre-existing Test 5 issue may still be
independent of this work.

## Risks And Things To Watch

### 1. Mixing two coherence layers

This design already has:

- L2 coherence above L2
- TLC coherence below L2

The fix must define a clean translation boundary rather than letting both
layers make conflicting ownership assumptions.

### 2. Probe response semantics

Make sure permission transitions are mapped correctly:

- downgrade vs invalidate
- dirty vs clean response
- when `ProbeAckData` is mandatory

An incorrect permission response can create very subtle false-coherence
behavior.

### 3. Beat granularity mismatch

The current bridge is still an 8x single-beat decomposition, not a true
burst path. That is acceptable for this fix, but be careful that:

- probe response data beat formatting matches adapter expectations
- line ownership semantics remain correct across all 8 beats

### 4. Deadlock risk

The new bridge and L2 snoop path must not create a circular wait such as:

- bridge waiting for L2
- L2 waiting for mem-side progress through the same bridge

This needs explicit thought in the state-machine design.

### 5. Dirty-data source of truth

Be very clear where dirty data comes from during probe handling:

- directly from L2's internal line state
- not from stale buffered bridge state

The bridge should report what L2 actually owns, not what the bridge last
requested.

## Recommended Implementation Order

1. Define and add the new snoop interface between `l2_tlc_bridge.v` and
   `rv64g_l2_cache.v`.
2. Implement the L2-side snoop FSM entry in `rv64g_l2_fsm.v`.
3. Make `l2_tlc_bridge.v` handle incoming probes and return probe acks.
4. Switch `l2_tlc_bridge.v` request generation from uncached traffic to
   coherent traffic.
5. Run targeted bridge/L2 tests.
6. Flip `tb_dma_l2_coherency_gap.v` from characterization mode to true
   regression mode.

## Non-Goals For This Work

- Converting the bridge to a true burst-capable TileLink adapter path
- Redesigning DMA to sit above L2 as a core-like client
- Refactoring the TLC fabric topology
- Solving unrelated pre-existing testbench issues outside this coherence
  path

## What Was Actually Implemented

This section records the final code changes that were added on top of the
plan above.

### `tlc/l2_tlc_bridge.v`

Implemented changes:

- added a real bridge-to-L2 snoop handshake:
  - `snoop_req_valid_o`
  - `snoop_req_addr_o`
  - `snoop_req_permissions_o`
  - `snoop_req_ready_i`
  - `snoop_rsp_valid_i`
  - `snoop_rsp_has_data_i`
  - `snoop_rsp_data_i`
  - `snoop_rsp_permissions_i`
  - `snoop_rsp_ready_o`
- changed refill reads from uncached requests to coherent read-miss
  requests so TLC can record L2 presence
- kept writes on the uncached path for now
- added internal probe tracking state so the bridge can:
  - accept a TLC probe request
  - forward it into L2 as a snoop
  - wait for the L2 snoop response
  - translate that result back into `probe_ack_from_l1_*`
- fixed the probe-ack handshake timing so
  `probe_ack_from_l1_valid` is held long enough for
  `l1_tilelink_adapter.v` to consume it

### `cache_system/rv64g_l2_cache.v`

Implemented changes:

- added the new external snoop request/response ports
- wired those ports directly into `rv64g_l2_fsm.v`

### `cache_system/rv64g_l2_fsm.v`

Implemented changes:

- added a new external snoop entry path from the bridge
- added `processing_snoop` mode tracking so the FSM can distinguish:
  - normal acquire/release traffic
  - externally-requested snoop handling
- added `ST_SNOOP_RSP` so L2 can return a snoop completion back to the
  bridge after directory/data updates are done
- reused the existing upper-level probe machinery so external snoops can
  still probe L1 holders above L2 before completing
- added snoop response bookkeeping:
  - whether data is returned
  - which permission downgrade/invalidate result is reported
- changed completion handling so external snoop operations do not
  deallocate the normal acquire MSHR path incorrectly

### `cache_system/rv64g_l2_mshr.v`

Implemented changes:

- fixed a same-cycle race between:
  - loading a new pending-probe mask
  - receiving a `ProbeAck` in that same cycle
- when both happen together, the pending mask is now loaded with that
  acknowledged bit already cleared

### `tlc/tlc_l2_dma_shared_mem_top.v`

Implemented changes:

- added all new bridge/L2 snoop wires
- connected the new handshake between `u_l2_bridge` and `u_l2`

### `cache_system/rv64g_cache_system.v`

Implemented changes:

- tied off the new snoop interface on the other `rv64g_l2_cache`
  instantiation so existing builds outside this DMA/L2 shared-memory top
  still compile cleanly

### `tlc/tb_dma_l2_coherency_gap.v`

Implemented changes:

- converted the test from hazard-characterization mode into fix-validation
  mode
- added a minimal upstream L1 probe responder in the testbench so L2 can
  receive real `ProbeAck` responses during the snoop flow
- made the responder return:
  - `NtoN` when no copy exists
  - `BtoB` for downgrade-to-branch
  - `BtoN` for invalidate
- updated the final verdict to require:
  - DMA write completes
  - DMA read-back confirms memory changed
  - later L2 re-acquire returns the DMA-written data
  - L2 performs a refetch instead of serving stale cached data

## Simulation Errors Encountered And Fixes

### 1. Icarus Verilog could not run this regression cleanly

Problems seen:

- duplicate/ordering issues while assembling the file list
- missing dependent memory modules
- unsupported unpacked-array task ports used by the testbench

Fix:

- switched the main debug/validation flow to Verilator for this
  regression

### 2. DMA write initially hung forever in STEP 2

Observed behavior:

- STEP 1 cached the line successfully
- DMA write started
- simulation timed out waiting for `dma_done`

Root cause:

- the testbench had no upstream L1 probe responder
- L2 issued a probe upward, but nothing answered it

Fix:

- added the minimal probe responder in
  `tlc/tb_dma_l2_coherency_gap.v`

### 3. DMA still hung after the testbench started returning `ProbeAck`

Observed behavior:

- testbench printed `TB_PROBE_ACK`
- DMA still never completed

Root cause:

- `l2_tlc_bridge.v` only pulsed `probe_ack_from_l1_valid` for one cycle
- `l1_tilelink_adapter.v` requires that valid and its data stay asserted
  through its `STATE_PROBE_ACK_SEND` state

Fix:

- changed the bridge to latch the snoop response and hold the
  `probe_ack_from_l1_*` bundle until the probe request is fully consumed

### 4. L2 accepted the upstream `ProbeAck`, but still did not finish the snoop

Observed behavior:

- L2 consumed the upstream `ProbeAck`
- no snoop completion came back to the bridge
- DMA remained stuck

Root cause:

- there was a same-cycle race in the L2 probe bookkeeping
- the `ProbeAck` could arrive in the same cycle that the pending-probe
  mask was first being loaded
- in that case, the ack looked "unexpected" and the pending bit handling
  was wrong

Fix:

- updated `rv64g_l2_fsm.v` so a same-cycle early `ProbeAck` is still
  accepted during `ST_CHECK`
- updated `rv64g_l2_mshr.v` so simultaneous `set_probes_i` and
  `probe_ack_i` correctly clear the acknowledged bit from the newly
  loaded mask

### 5. Regression output still reported failure even after the RTL worked

Observed behavior:

- DMA completed
- memory read-back was correct
- L2 re-acquired fresh data
- test still failed

Root cause:

- the testbench verdict still contained old hazard-era expectations:
  - stale data expected
  - no new memory reads expected

Fix:

- rewrote the verdict checks in `tlc/tb_dma_l2_coherency_gap.v` to match
  the fixed coherency behavior
- updated the pass/fail messaging accordingly

## Definition Of Done

This work is done when all of the following are true:

- DMA write to a line held in L2 triggers a real probe to L2.
- L2 responds correctly with downgrade/invalidate behavior.
- Dirty data is returned when required.
- DMA write completes only after probe resolution.
- A subsequent L2/core read does not observe stale data.
- The main TLC/L2/DMA regression tests pass with the new expectation.
